# Migrating from `@neshca/cache-handler`

This guide covers migrating from [`@neshca/cache-handler`](https://www.npmjs.com/package/@neshca/cache-handler) — and its forks, including [`@jadkins89/next-cache-handler`](https://www.npmjs.com/package/@jadkins89/next-cache-handler), which describes itself as a "temporary fork" of neshca with a Next 15 patch. The API mapping below applies to both.

First, credit where it's due: neshca defined this space. Its handler layering, instrumentation-based cache seeding, and TTL model shaped how everyone (including this package) thinks about shared Next.js caches, and it was the community example linked from the Next.js docs for years.

## Why migrate

- neshca's last publish was **2024-11-26** (v1.9.0). Its peer range is `next >= 13.5.1 < 15`.
- On Next 15/16 projects, `npm install` doesn't fail — it **silently downgrades `next` to 14.x** to satisfy that peer range (reproducible with the official `cache-handler-redis` example: `next: latest` resolves to 14.2.35 with no warning).
- Next 16's `'use cache'` / `cacheHandlers` (plural) interface didn't exist when neshca was last released, so that entire layer is uncovered.

If you're staying on Next 13/14, neshca still works — this guide is for projects moving to 15/16.

## TL;DR

```bash
npm uninstall @neshca/cache-handler        # or @jadkins89/next-cache-handler
npm install @leejpsd/nextjs-cache-handler redis
npx nextjs-cache-handler init --yes
# follow the printed next.config keys, set REDIS_URL + DEPLOYMENT_VERSION, then:
npx nextjs-cache-handler doctor
```

Delete `cache-handler.mjs` and the `registerInitialCache` call in `instrumentation.ts` — both are replaced below.

## Concept mapping

| neshca | here |
| --- | --- |
| `cache-handler.mjs` with `CacheHandler.onCreation(async ({ buildId }) => …)` | Generated `cache-incremental.cjs` (and `cache-components.cjs` on Next 16.1+) — plain module config, no creation hook |
| `handlers: [redisHandler, localHandler]` layering | Single Redis layer with a **built-in bounded in-memory fallback** that activates when Redis is unreachable (it is a failure fallback, not a read-through L1) |
| `redis-strings` — `createHandler({ client, keyPrefix, sharedTagsKey, timeoutMs, revalidateTagQuerySize })` | `REDIS_URL` env (client is created for you); optional `keyPrefix`. Tags are stored per entry plus tag-state keys — there is no shared tags hash to size or query |
| `local-lru` handler | Built-in fallback LRU (bounded, ~1000 entries) — nothing to configure |
| `experimental-redis-cluster` | Cluster is supported non-experimentally (`hashTag` option, real 3-master cluster e2e in CI) |
| `ttl: { defaultStaleAge, estimateExpireAge }` | No manual TTL math — each record stores the `revalidate` Next.js provided for it, and Redis TTLs are derived from it (clamped to sane bounds) |
| `buildId` from the `onCreation` context for key scoping | `DEPLOYMENT_VERSION` env — explicit deploy-scoped namespacing, decoupled from the build hash. Old and new deploys coexist in the same Redis; nothing is flushed |
| `registerInitialCache` in `instrumentation.ts` (seeds at app boot, in-process) | `npx nextjs-cache-handler seed` — a **build/deploy-time step** (Dockerfile or CI). Writes with `NX`, so a late-starting container can never overwrite an entry a live instance just wrote |
| `neshClassicCache` (`getServerSideProps` / API route caching) | **No equivalent yet** — it's on the roadmap. If you depend on it, that's a real blocker; stay put or wrap those call sites yourself |
| `redis-stack` handler (RedisJSON storage) | Not supported — entries are strings, with optional `compression: "gzip" \| "brotli"` |
| — (nothing existed) | Next 16 `'use cache'` support via the plural `cacheHandlers` interface: soft (`revalidateTag(tag, "max")` = stale-while-revalidate) vs hard (`updateTag`) semantics, cross-instance tag propagation (polling by default, optional pub/sub) |

## Config change

Before (neshca):

```js
// next.config.js
module.exports = {
  cacheHandler: require.resolve('./cache-handler.mjs'),
  cacheMaxMemorySize: 0,
}
```

After:

```js
// next.config.js
module.exports = {
  cacheHandler: require.resolve('./cache-incremental.cjs'),
  // Next 16.1+ with cacheComponents only:
  cacheHandlers: { default: require.resolve('./cache-components.cjs') },
  cacheMaxMemorySize: 0, // keep this — same reason as with neshca
}
```

Both `.cjs` files are generated by `init` and are meant to be committed and edited.

## Seeding replacement

Where neshca seeded at application boot via instrumentation, run seeding as a deploy step after `next build`:

```bash
npx nextjs-cache-handler seed --namespace "$DEPLOYMENT_VERSION"
# flags: [--dir .next] [--key-prefix <p>] [--hash-tag] [--compression gzip|brotli]
```

Same effect (no cold-start MISS storm on new deploys), but it runs once per deploy instead of once per instance boot, and `NX` writes make it safe during rolling deploys.

## Coexistence and rollback

Key shapes don't overlap (`next-incremental:entry:<namespace>:<key>` here vs neshca's `keyPrefix` scheme), so both packages can point at the same Redis during a migration without corrupting each other. Rolling back is reverting the `next.config` change — old entries will simply age out via TTL.

## Verify

```bash
npx nextjs-cache-handler doctor        # checks config wiring, Redis reachability, env
```

Then the usual smoke: request a cached route twice (`x-nextjs-cache: HIT` on the second), `revalidateTag` from one instance, confirm another instance picks it up.

Something not covered here, or a neshca behavior you can't replicate? [Open an issue](https://github.com/leejpsd/nextjs-cache-handler/issues) — migration gaps get priority.
